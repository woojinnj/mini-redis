# Mini Redis · 동시성과 캐시 무효화

저희 조는 AI로 Mini Redis를 각각 만든 뒤, 정글 가이드라인에서 **동시성**과 **캐시 무효화**를 골라 두 코드를 비교했습니다. 비교 결과를 바탕으로 **코드 2의 Redis 서버와 코드 1의 상품 API 무효화 방식을 결합하기로 했습니다.** 아래는 각 구현의 장단점과 그 판단의 근거입니다. 결합 구현과 검증은 다음 단계입니다.

| 구분 | Redis 서버 | HTTP API 데모 |
|---|---|---|
| **코드 1 · 이 저장소** | Python, 연결마다 스레드를 두는 방식 | 상품 조회·수정, 상품별 락과 버전 키로 캐시 무효화 |
| **코드 2 · 팀원 저장소** | C, 단일 스레드 이벤트 루프 방식 | 사용자 조회, 별도 요청으로 캐시 삭제 |

두 HTTP API 데모는 모두 Python으로 작성됐습니다. 아래 동시성 비교는 **Redis 서버**, 무효화 비교는 **HTTP API**의 동작을 다룹니다.

## 1. 동시성 · 여러 요청이 겹칠 때

**스레드**는 프로그램 안에서 일을 처리하는 단위입니다. 두 코드 모두 저장소에서 데이터를 읽거나 바꾸는 일은 하나씩 처리합니다. 차이는 한 요청을 처리하는 동안 다른 요청을 어디까지 받을 수 있는지에 있습니다.

| 방식 | 좋은 점 | 감수할 점 |
|---|---|---|
| **코드 1 · 멀티 스레드** | 연결마다 담당 스레드가 있음. 한 연결이 데이터를 기다리는 동안 다른 스레드는 자기 요청을 처리할 수 있음 | 저장소는 전역 락으로 보호하므로 명령들이 동시에 저장소를 사용할 수 없음. 연결마다 스레드 자원이 필요함 |
| **코드 2 · 단일 스레드** | 이벤트 루프가 읽거나 쓸 준비가 된 연결을 골라 처리함. 연결마다 스레드를 만들거나 저장소 락을 경쟁할 필요가 없음 | A의 명령이 오래 걸리면 B의 요청이 도착해 있어도 읽는 일부터 늦어짐 |

**스레드가 많아도 저장소 처리량이 늘지 않을 수 있습니다.** 코드 1은 스레드가 여러 개여도 저장소 작업은 락 때문에 하나씩 처리합니다. 이때 스레드 사이에서 실행을 넘기거나 락을 기다리는 비용이 생길 수 있습니다. 코드 2는 한 스레드가 준비된 요청을 차례로 실행하므로 이런 비용을 줄일 수 있습니다. 특히 메모리에서 짧게 끝나는 `GET`·`SET`에서는 이 차이가 처리량에 영향을 줄 수 있습니다.

다만 단일 스레드가 항상 빠른 것은 아닙니다. 긴 명령은 이벤트 루프 전체를 붙잡고, 멀티 스레드는 한 연결의 통신 대기 중에도 다른 연결을 처리할 수 있습니다. 실제 성능은 명령의 종류, 대기 시간, 구현 언어와 코드에 따라 달라집니다.

## 2. 무효화 · 원본이 바뀐 뒤 예전 값을 쓰지 않기

**캐시**에는 다음에 다시 쓸 수 있도록 조회 결과를 잠시 저장합니다. **무효화**는 그 결과가 오래됐을 때 더 이상 쓰지 않게 하는 일입니다.

| 방식 | 좋은 점 | 감수할 점 |
|---|---|---|
| **코드 1 · 상품을 고칠 때 함께 처리** | 상품을 고치면 캐시를 찾는 이름인 **키**의 버전도 바뀜. 예전 값이 남아 있어도 수정 완료 후 시작한 조회는 새 키를 사용함 | 같은 상품을 읽는 쪽이 먼저 시작해 캐시를 채우고 있으면, 고치는 쪽은 기다려야 함 |
| **코드 2 · 캐시 삭제를 따로 요청** | 원하는 때에 특정 사용자의 캐시만 지울 수 있음 | 지울 때를 요청하는 쪽이 정해야 함. 먼저 시작한 조회가 늦게 끝나면 지운 자리에 값을 다시 저장할 수 있음 |

코드 1은 **상품별 락**으로 같은 상품의 조회·캐시 채우기·수정을 차례로 처리하고, **버전 키**로 이전 캐시의 삭제에 실패해도 그 값을 다시 조회하지 않게 합니다. 이 동작은 **같은 API 프로세스 안에서** 보장됩니다. API를 여러 개 띄우면 상품 데이터·버전·락도 각각 따로 가지므로, 여러 프로세스가 같은 원본을 다루려면 별도 설계가 필요합니다.

코드 2의 데모에는 원본 수정 API가 없고 캐시 삭제만 있습니다. 따라서 이 비교는 각 데모가 수정과 무효화를 어디까지 다루는지 보여줍니다. 코드 1의 무효화 방식은 API에 구현돼 있어, 코드 2의 Redis 서버와 결합할 수 있는 부분입니다.

## 3. 팀의 결론 · 두 코드의 장점 결합

### 동시 요청 처리량은 코드 2가 높았습니다

같은 컴퓨터에서 두 서버에 조회(`GET`) 90%, 저장(`SET`) 10%의 비율로 명령을 보냈습니다.

| 동시 연결 수 | 코드 1 · 초당 처리 건수 | 코드 2 · 초당 처리 건수 |
|---|---:|---:|
| 1개 | 25,610 | 29,791 |
| 16개 | 51,091 | 143,193 |

동시 연결 16개에서 **코드 2의 처리량은 코드 1의 약 2.8배**였습니다. 다만 코드 1은 Python, 코드 2는 C로 작성됐고 세부 구현도 다릅니다. 앞서 설명한 스레드·락 비용은 성능에 영향을 줄 수 있는 요인이지만, **이 측정만으로 2.8배의 차이를 단일 스레드의 효과라고 단정할 수는 없습니다.** 스레드 구조의 영향만 확인하려면 언어와 나머지 조건을 맞춘 추가 비교가 필요합니다.

### 팀의 판단

| 결합할 부분 | 근거와 기대하는 동작 |
|---|---|
| **Redis 서버 · 코드 2** | 이번 `GET`·`SET` 측정에서 더 높은 처리량을 보인 C 이벤트 루프 서버를 기반으로 삼습니다. |
| **상품 API · 코드 1** | 상품별 락과 버전 키를 유지해, 같은 API 프로세스에서 수정 완료 후 시작한 조회가 이전 버전의 캐시를 사용하지 않게 합니다. |

저희는 **코드 2의 명령 처리 성능과 코드 1의 수정·무효화 동작을 함께 가져가기로 했습니다.** Redis 서버는 명령을 처리하고, 상품 API는 원본 수정과 캐시 사용 순서를 조정하도록 결합할 계획입니다. Redis 명령을 하나씩 실행하는 것만으로는 API의 여러 명령에 걸친 조회·수정 과정까지 보호할 수 없으므로, API의 상품별 락과 버전 키도 유지합니다.

다음 단계에서는 두 코드의 명령·응답 호환성을 확인하고, 결합한 상품 API에 동시 조회·수정 요청을 보내 이전 캐시가 다시 사용되지 않는지 검증하겠습니다. API의 처리량과 응답 시간도 다시 측정해야 합니다. 위 표의 2.8배는 Redis 서버를 직접 측정한 결과이며, 결합한 API의 성능 향상을 보장하는 수치는 아닙니다.
