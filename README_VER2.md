<a id="concurrency"></a>

## 1. 동시성 · 여러 요청이 겹칠 때

**스레드**는 프로그램 안에서 일을 처리하는 단위입니다. 두 코드 모두 저장소에서 데이터를 읽거나 바꾸는 일은 하나씩 처리합니다. 차이는 한 요청을 처리하는 동안 다른 요청을 어디까지 받을 수 있는지에 있습니다.

| 방식 | 좋은 점 | 감수할 점 |
|---|---|---|
| **현재 코드 · 멀티 스레드** | 연결마다 담당 스레드가 있음. A가 저장소를 쓰는 동안 B의 스레드는 요청을 미리 읽을 수 있음 | B도 저장소를 쓰려면 기다려야 함. 연결만 해 두고 요청을 보내지 않아도 스레드 하나가 필요함 |
| **비교 코드 · 단일 스레드** | 스레드 하나가 요청이 들어온 연결을 골라 처리함. 연결마다 스레드를 만들 필요가 없음 | A의 명령이 오래 걸리면 B의 요청이 도착해 있어도 읽는 일부터 늦어짐 |

<a id="invalidation"></a>

## 2. 무효화 · 원본이 바뀐 뒤 예전 값을 쓰지 않기

**캐시**에는 다음에 다시 쓸 수 있도록 조회 결과를 잠시 저장합니다. **무효화**는 그 결과가 오래됐을 때 더 이상 쓰지 않게 하는 일입니다.

| 방식 | 좋은 점 | 감수할 점 |
|---|---|---|
| **현재 코드 · 상품을 고칠 때 함께 처리** | 상품을 고치면 캐시를 찾는 이름인 **키**도 바뀜. 예전 값이 남아 있어도 다음 조회는 새 키를 사용함 | 같은 상품을 읽는 쪽이 먼저 시작해 캐시를 채우고 있으면, 고치는 쪽은 기다려야 함 |
| **비교 코드 · 캐시 삭제를 따로 요청** | 원하는 때에 특정 사용자의 캐시만 지울 수 있음 | 지울 때를 요청하는 쪽이 정해야 함. 먼저 시작한 조회가 늦게 끝나면 지운 자리에 값을 다시 저장할 수 있음 |

현재 코드에서 같은 상품의 조회와 수정이 차례를 지키는 것은 **같은 API 프로그램 안에서**입니다. 프로그램을 여러 개 띄우면 각각 자기 락을 씁니다.

## 3. 현재 코드를 선택한 이유

**같은 컴퓨터에서 조회(`GET`) 90%, 저장(`SET`) 10%로 측정한 결과**

| 동시 연결 수 | 현재 코드 · 초당 처리 건수 | 비교 코드 · 초당 처리 건수 |
|---|---:|---:|
| 1개 | 25,610 | 29,791 |
| 16개 | 51,091 | 143,193 |

| 선택할 때 본 점 | 팀의 판단 |
|---|---|
| **감수한 성능 차이** | 동시 연결 16개에서 비교 코드가 초당 약 2.8배의 Redis 명령을 처리함 |
| **우선한 사용자 경험** | 사용자가 상품을 고치고 다시 열었을 때 수정한 내용이 보여야 함. 예전 내용이 뜨면 수정이 반영됐는지 확인할 수 없음 |
| **구현에서 확인한 근거** | 현재 상품 API는 수정할 때 캐시 키의 버전도 올림. 예전 캐시가 남아도 다음 조회는 새 키를 사용함 |

비교 코드의 예제는 사용자 캐시를 따로 지우는 기능을 제공합니다. 이 방식을 상품 수정에 쓰려면 수정과 캐시 삭제를 연결하고, 삭제에 실패하는 경우도 처리해야 합니다. **저희는 수정 직후의 조회까지 이미 처리하는 현재 코드를 선택했습니다.**

<details>
<summary>측정 조건 · 비교한 코드 · 관련 문서</summary>

macOS(arm64)에서 현재 코드(Python 3.13.2, `7907b3a`)와 비교 코드(C, `-O2`, `bfb1c05`)를 번갈아 실행했습니다. 같은 클라이언트가 연결을 유지하고, 연결마다 자기 키에 32바이트 값을 읽고 썼습니다. 준비 요청 후 회당 총 16,000건을 보냈고, 연결마다 응답을 받은 뒤 다음 명령을 보냈습니다. 표는 조건별 4회 측정의 중앙값입니다.

응답 시간도 클라이언트에서 쟀습니다. 요청 100건 중 95건이 응답을 받은 시간(p95)은 연결 1개에서 현재 코드 0.043ms, 비교 코드 0.036ms였고, 연결 16개에서는 각각 0.638ms와 0.117ms였습니다. 이 수치는 Redis 명령을 직접 보낸 결과이며 상품 API의 응답 시간은 별도로 측정하지 않았습니다.
