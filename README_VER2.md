# Mini Redis · 동시성과 캐시 무효화

저희 조는 AI로 Mini Redis를 각각 만든 뒤, 정글 가이드라인의 **동시성**과 **캐시 무효화**를 기준으로 두 코드를 비교했습니다. Redis 서버에는 **코드 2의 단일 스레드 방식**을, 상품 API에는 **코드 1의 상품별 락과 버전 키**를 적용하기로 했습니다. 실제 결합과 검증은 다음 단계입니다.

| 구분 | Redis 서버 | HTTP API 데모 |
|---|---|---|
| **코드 1** | Python, 연결마다 스레드를 두는 멀티 스레드 방식 | 상품 조회·수정, 상품별 락과 버전 키로 캐시 무효화 |
| **코드 2** | C, 단일 스레드 방식 | 사용자 조회, 별도 요청으로 캐시 삭제 |

두 HTTP API 데모는 모두 Python으로 작성됐습니다. 아래 동시성 비교는 **Redis 서버**, 무효화 비교는 **HTTP API**의 동작을 다룹니다.

| 발표 순서 | 살펴볼 내용 |
|---|---|
| [1. 동시성](#concurrency) | 여러 요청이 겹칠 때 처리하는 방법 |
| [2. 무효화](#invalidation) | 원본이 바뀌면 예전에 저장한 결과를 다시 쓰지 않는 방법 |
| [3. 팀의 결론](#selection) | 처리량 측정 결과와 두 코드의 장점을 결합할 방향 |

## 1. 동시성 · 여러 요청이 겹칠 때

**스레드**는 프로그램 안에서 일을 처리하는 단위입니다. 두 코드 모두 저장소에서 데이터를 읽거나 바꾸는 일은 하나씩 처리합니다. 차이는 한 요청을 처리하는 동안 다른 요청을 어디까지 받을 수 있는지에 있습니다.

| 방식 | 좋은 점 | 감수할 점 |
|---|---|---|
| **코드 1 · 멀티 스레드** | 연결마다 담당 스레드가 있음. 한 연결이 데이터를 기다리는 동안 다른 스레드는 자기 요청을 처리할 수 있음 | 저장소는 전역 락으로 보호하므로 명령들이 동시에 저장소를 사용할 수 없음. 연결마다 스레드 자원이 필요함 |
| **코드 2 · 단일 스레드** | 이벤트 루프가 읽거나 쓸 준비가 된 연결을 골라 처리함. 연결마다 스레드를 만들거나 저장소 락을 경쟁할 필요가 없음 | A의 명령이 오래 걸리면 B의 요청이 도착해 있어도 읽는 일부터 늦어짐 |

짧은 `GET`·`SET`이 몰리면, 코드 1에서는 스레드 전환과 저장소 락 대기가 처리량에 영향을 줄 수 있습니다. 코드 2는 이런 비용을 줄일 수 있지만, 긴 명령을 처리하는 동안 다른 요청도 기다립니다.

<a id="invalidation"></a>

## 2. 무효화 · 원본이 바뀐 뒤 예전 값을 쓰지 않기

**캐시**에는 다음에 다시 쓸 수 있도록 조회 결과를 잠시 저장합니다. **무효화**는 그 결과가 오래됐을 때 더 이상 쓰지 않게 하는 일입니다.

| 방식 | 좋은 점 | 감수할 점 |
|---|---|---|
| **코드 1 · 상품을 고칠 때 함께 처리** | 상품을 고치면 캐시를 찾는 이름인 **키**의 버전도 바뀜. 예전 값이 남아 있어도 수정 완료 후 시작한 조회는 새 키를 사용함 | 같은 상품을 읽는 쪽이 먼저 시작해 캐시를 채우고 있으면, 고치는 쪽은 기다려야 함 |
| **코드 2 · 캐시 삭제를 따로 요청** | 원하는 때에 특정 사용자의 캐시만 지울 수 있음 | 지울 때를 요청하는 쪽이 정해야 함. 먼저 시작한 조회가 늦게 끝나면 지운 자리에 값을 다시 저장할 수 있음 |

코드 1은 **상품별 락**으로 같은 상품의 조회·캐시 채우기·수정을 차례로 처리하고, **버전 키**로 이전 캐시의 삭제에 실패해도 그 값을 다시 조회하지 않게 합니다. 이 동작은 **같은 API 프로세스 안에서** 보장됩니다. API를 여러 개 띄우면 상품 데이터·버전·락도 각각 따로 가지므로, 여러 프로세스가 같은 원본을 다루려면 별도 설계가 필요합니다.

코드 2의 데모는 사용자 조회와 캐시 삭제를 제공하며, 삭제 요청은 캐시에 저장된 복사본에만 적용됩니다. 코드 1의 상품별 락과 버전 키는 상품 API에서 관리합니다. 따라서 Redis 서버의 스레드 방식과 별개로 선택할 수 있습니다.

## 3. 팀의 결론 · 두 코드의 장점 결합

### 동시 요청 처리량은 코드 2가 높았습니다

같은 컴퓨터에서 두 서버에 조회(`GET`) 90%, 저장(`SET`) 10%의 비율로 명령을 보냈습니다.

| 동시 연결 수 | 코드 1 · 초당 처리 건수 | 코드 2 · 초당 처리 건수 |
|---|---:|---:|
| 1개 | 25,610 | 29,791 |
| 16개 | 51,091 | 143,193 |

동시 연결 16개에서 **코드 2의 처리량은 코드 1의 약 2.8배**였습니다. 이 결과에는 스레드 방식과 함께 구현 언어(Python과 C), 명령 처리 코드의 차이도 반영돼 있습니다.

### 팀의 판단

| 비교 기준 | 선택한 방식 | 선택 이유 |
|---|---|---|
| **동시성 · Redis 서버** | **코드 2의 단일 스레드 방식** | 한 스레드가 준비된 요청을 골라 처리하므로 연결마다 스레드를 만들거나 스레드끼리 저장소 락을 기다릴 필요가 없습니다. |
| **캐시 무효화 · 상품 API** | **코드 1의 상품별 락과 버전 키** | 같은 상품의 조회와 수정은 락으로 순서를 지킵니다. 수정 완료 후 시작한 조회는 새 키를 쓰므로, 예전 캐시를 지우지 못해도 수정된 내용을 읽습니다. |

단일 스레드 방식은 **Redis 명령 하나씩** 처리하는 순서를 정합니다. 상품별 락과 버전 키는 **같은 API 프로세스에서** 여러 단계에 걸친 상품 조회와 수정의 순서를 지키고, 수정 후에 어떤 캐시를 읽을지 정합니다.

두 방식을 결합한 뒤에는 상품 조회와 수정이 겹칠 때의 동작과 상품 API의 처리량을 확인할 계획입니다.
