# Mini Redis · 동시성과 캐시 무효화

Mini Redis는 여러 클라이언트가 키와 값을 읽고 쓰는 메모리 저장소입니다. 정글 가이드라인의 두 기준으로 현재 코드와 비교 코드의 설계 선택을 살펴봤습니다.

| 순서 | 비교 기준 |
|---|---|
| [1. 동시성](#concurrency) | 여러 요청이 같은 저장소를 쓸 때, 누가 어떤 작업을 기다리는가 |
| [2. 무효화](#invalidation) | 원본이 바뀐 뒤, 이전 캐시를 누가 어떻게 무효화하는가 |
| [3. 선택 이유](#selection) | 상품 수정 후 첫 조회에서 중요하게 본 동작 |

<a id="concurrency"></a>

## 1. 동시성 · 여러 요청이 공유 저장소를 쓰는 구조

**공통점** · 두 코드 모두 저장소 연산은 한 번에 하나씩 처리합니다. 긴 저장소 연산 뒤에 짧은 조회가 들어오면 둘 다 기다릴 수 있습니다.

| 설계 선택 | 얻는 점 | 감수하는 비용 |
|---|---|---|
| **현재 코드** · 연결별 스레드 | 저장소 락(`RLock`) 밖에서는 각 스레드가 자기 연결의 입력을 읽고 응답을 보낼 수 있음 | 요청을 보내지 않고 연결만 유지하는 클라이언트에도 스레드 하나가 필요 |
| **비교 코드** · 단일 이벤트 루프 | 한 스레드가 준비된 연결을 골라 처리하므로 연결별 스레드와 저장소 락이 필요 없음 | 긴 명령을 실행하는 동안에는 루프가 다른 연결에서 이미 도착한 요청을 읽는 일도 미뤄짐 |

<a id="invalidation"></a>

## 2. 무효화 · 다음 조회에서 예전 값을 쓰지 않는 방법

| 설계 선택 | 얻는 점 | 감수하는 비용 |
|---|---|---|
| **현재 코드** · `PUT /products/1`에서 가격과 캐시 버전을 함께 변경 | 호출자는 가격만 수정. 예전 키 삭제가 실패해도 다음 조회는 새 키를 사용 | 같은 상품의 캐시 조회가 원본 응답을 기다리는 동안 수정도 대기. 상품별 락은 API 한 프로세스 안에서만 공유 |
| **비교 코드** · `DELETE /users/1`로 특정 캐시를 직접 삭제 | 호출자가 대상과 시점을 정할 수 있고, 진행 중인 원본 조회가 끝나기 전에 삭제 요청을 마칠 수 있음 | 삭제 시점을 호출자가 챙겨야 함. 먼저 시작한 조회가 삭제 뒤 같은 키를 다시 채울 수 있음 |

**삭제 시도 직후의 첫 조회** · 다른 요청이 끼어들지 않고 캐시를 읽을 수 있는 경우

| | 현재 코드 · 상품 가격을 1,000원에서 1,200원으로 수정 | 비교 코드 · 사용자 캐시 삭제 요청 |
|---|---|---|
| 첫 조회가 찾는 키 | 가격 수정 때 버전을 올렸으므로 **새 키 `v2`** | 삭제 전과 **같은 키 `user:1`** |
| 이전 키 삭제 성공 | `v2`가 비어 원본의 1,200원을 읽음 | `user:1`이 비어 사용자 원본을 다시 읽음 |
| 삭제 실패로 이전 값이 남음 | `v1`에 1,000원이 남아도 `v2`를 찾아 원본의 1,200원을 읽음 | `user:1`에 만료 전 값이 남아 있으면 그 값을 반환할 수 있음 |

비교 코드의 삭제 요청은 사용자 **캐시**만 지웁니다. 원본에서 다시 읽더라도 사용자 정보가 같을 수 있습니다.

<a id="selection"></a>

## 3. 현재 코드를 선택한 이유

**현재 코드는 가격을 수정한 뒤 예전 키 삭제에 실패해도, 다음 조회에서 그 키를 읽지 않습니다.**

| 선택 기준 | 팀의 판단 |
|---|---|
| **동시성** | 현재 코드는 연결마다 스레드가 필요하고, 비교 코드는 긴 명령 하나가 다른 연결의 요청 처리를 늦출 수 있음. 이 차이만으로는 어느 한쪽을 고르기 어려웠음 |
| **무효화** | 같은 상품의 조회와 수정이 겹치면 한쪽이 기다리지만, 가격을 바꾸는 쪽은 수정 요청만 보내면 됨. 다음 조회가 새 버전 키를 쓰므로 이전 캐시의 삭제 성공 여부에 의존하지 않음 |
