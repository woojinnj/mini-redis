# Mini Redis · 동시성과 캐시 무효화

저희 조는 AI로 Mini Redis를 각각 만든 뒤, 정글 가이드라인의 **동시성**과 **캐시 무효화**를 기준으로 두 코드를 비교했습니다.

[1. 동시성](#concurrency) · [2. 캐시 무효화](#invalidation) · [3. 팀의 결론](#selection)

## 비교 대상

| 구분 | Redis 서버 | HTTP API 데모 |
|---|---|---|
| **코드 1** | Python · 연결마다 스레드를 두는 멀티 스레드 | 상품 조회·수정 · 상품별 락과 버전 키 |
| **코드 2** | C · 단일 스레드 | 사용자 조회 · 별도 요청으로 캐시 삭제 |

동시성은 Redis 서버에서, 캐시 무효화는 HTTP API에서 비교했습니다. 두 API 데모는 모두 Python으로 작성됐습니다.

<a id="concurrency"></a>

## 1. 동시성

스레드는 프로그램 안에서 일을 처리하는 단위입니다. 두 코드 모두 저장소 작업은 하나씩 처리하고, 여러 연결을 맡는 방식이 다릅니다.

| 방식 | 좋은 점 | 감수할 점 |
|---|---|---|
| **코드 1 · 멀티 스레드** | 한 연결이 통신을 기다리는 동안 다른 스레드가 자기 요청을 읽을 수 있음 | 연결마다 스레드가 필요함. 저장소 락을 다른 스레드가 잡고 있으면 기다림 |
| **코드 2 · 단일 스레드** | 한 스레드가 준비된 연결을 골라 처리함. 스레드끼리 저장소 락을 두고 기다릴 일이 없음 | 긴 명령이 끝날 때까지 다른 요청도 기다림 |


<a id="invalidation"></a>

## 2. 캐시 무효화

**캐시**는 조회 결과를 잠시 저장해 두는 곳입니다. **무효화**는 원본이 바뀐 뒤 예전 결과를 다시 쓰지 않게 하는 일입니다.

| 방식 | 좋은 점 | 감수할 점 |
|---|---|---|
| **코드 1 · 상품 수정과 함께 처리** | 수정이 끝난 뒤 시작한 조회는 새 키를 사용함 | 같은 상품의 조회가 캐시를 채우는 동안 수정 요청은 기다림 |
| **코드 2 · 별도로 삭제 요청** | 원하는 때에 특정 사용자의 캐시만 지울 수 있음 | 요청하는 쪽이 삭제 시점을 정함. 진행 중인 조회가 지운 자리에 값을 다시 채울 수 있음 |

## 3. 팀의 결론

### 동시성 · 코드 2의 단일 스레드 방식

Redis 서버는 한 스레드가 준비된 요청을 골라 처리하도록 설계하기로 했습니다. 연결별 스레드 생성 비용과 저장소 락 대기를 줄일 수 있습니다.

같은 컴퓨터에서 조회(`GET`) 90%, 저장(`SET`) 10%의 비율로 측정했습니다.

| 동시 연결 수 | 코드 1 · 초당 처리 건수 | 코드 2 · 초당 처리 건수 |
|---|---:|---:|
| 1개 | 25,610 | 29,791 |
| **16개** | 51,091 | **143,193** |

동시 연결 16개에서 **코드 2의 처리량은 코드 1의 약 2.8배**였습니다. 구현 언어와 명령 처리 코드의 차이도 반영된 결과입니다.

### 캐시 무효화 · 코드 1의 상품별 락과 버전 키

예전 캐시가 남아 있어도 **상품을 수정한 뒤 다시 열면 방금 고친 내용을 볼 수 있습니다.**
