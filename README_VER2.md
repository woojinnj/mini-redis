# Mini Redis · 두 요청이 겹치면 어떻게 될까?

Mini Redis는 키와 값을 메모리에 보관하고, 다른 프로그램이 명령을 보내 읽고 쓸 수 있게 만든 서버입니다. 두 구현을 정글 가이드라인의 **동시성**과 **무효화** 기준으로 비교했습니다.

| 살펴볼 순서 | 질문 |
|---|---|
| [동시성](#concurrency) | 두 사람이 동시에 숫자를 1씩 올리면 둘 다 반영될까? |
| [무효화](#invalidation) | 가격을 바꾼 뒤 첫 조회에서 예전 가격이 나올 수 있을까? |
| [선택 이유](#selection) | 우리 팀은 어떤 동작을 더 중요하게 봤을까? |

<a id="concurrency"></a>

## 1. 동시성 · 0에서 두 번 올리면 2

**두 클라이언트가 같은 키에 `INCR`를 한 번씩 보냅니다.** 각 명령은 값을 읽고, 1을 더하고, 결과를 저장합니다.

| | 현재 구현 · Python 서버 | 팀원 구현 · C 서버 |
|---|---|---|
| 누가 처리하나 | 연결마다 스레드를 두고 요청을 처리 | 한 스레드의 이벤트 루프가 여러 연결을 처리 |
| 증가가 겹치면 | 한 스레드가 공유 저장소 락(`RLock`) 안에서 읽기와 쓰기를 마치면 다음 스레드가 진입 | 이벤트 루프가 첫 명령을 끝낸 뒤 다음 명령을 실행 |
| 장점과 비용 | 다른 연결의 입력을 받을 수 있음. 저장소 락을 오래 잡으면 다른 키의 요청도 대기 | 저장소 락과 연결별 스레드가 필요 없음. 긴 명령은 같은 루프의 다음 명령을 지연 |

| 같은 키를 증가시키는 두 방법 | 가능한 실행 순서 | 최종값 |
|---|---|---|
| 각자 `INCR` 한 번 | A가 0 → 1 저장, B가 1 → 2 저장 | **2** |
| 각자 `GET` 후 계산하고 `SET` | A와 B 모두 0을 읽고, 각자 1을 저장 | **1이 될 수 있음** |

> **명령 하나가 끝까지 실행돼도, 여러 명령 사이에는 다른 요청이 들어올 수 있습니다.** 캐시를 읽고 다시 채우는 과정에서도 같은 문제가 생깁니다.

<a id="invalidation"></a>

## 2. 무효화 · 가격을 1,000원에서 1,200원으로 바꾸면

**무효화**는 이전에 저장한 응답을 다음 조회에서 다시 쓰지 않도록 하는 일입니다.

| | 현재 구현 · 상품 API | 팀원 구현 · 사용자 API |
|---|---|---|
| 시작점 | 상품 수정 요청 `PUT /products/1` | 캐시 삭제 요청 `DELETE /users/1` |
| 키 처리 | 상품별 락 안에서 원본 수정 → 버전 증가 → 이전 키 삭제 시도 | 해당 사용자의 캐시 키 `user:1`에 `DEL` 실행 |
| 다음 조회 | 새 버전의 키를 조회. 캐시가 비면 바뀐 가격으로 채움 | 같은 키를 조회. 캐시가 비면 사용자 정보로 다시 채움 |

**팀원 구현에서 조회와 삭제가 겹치는 한 가지 순서**

| 순서 | 사용자 조회 A | 캐시 삭제 B |
|---|---|---|
| ① | `GET user:1` → 캐시가 비어 원본 조회 시작 | |
| ② | 원본 응답을 기다림 | `DEL user:1` 처리 완료 |
| ③ | 원본 응답을 받아 `SET user:1` | |

삭제 요청 뒤 같은 키가 다시 채워질 수 있습니다. 팀원 데모가 제공하는 것은 사용자 조회와 명시적 캐시 삭제입니다.

**현재 구현에서 같은 상품을 조회하고 수정할 때**

- **상품별 락**이 순서를 정합니다. 먼저 시작한 캐시 조회가 락을 잡았다면 캐시를 채울 때까지 수정이 기다립니다. 수정이 먼저 락을 잡으면 이후 조회는 수정이 끝난 뒤 진행합니다.
- **버전 키**가 읽을 대상을 정합니다. 수정 전 키 `v1`에 1,000원이 남아 있어도 다음 조회는 `v2`를 찾아 1,200원을 읽습니다. 여기서 `v1`, `v2`는 상품 키의 버전 부분입니다.

<a id="selection"></a>

## 왜 현재 구현을 선택했나?

**상품을 수정하는 사람이 예전 캐시까지 따로 지울 필요가 없기 때문입니다.**

| 팀원 구현이 편리한 경우 | 현재 구현을 선택한 기준 | 현재 구현의 한계 |
|---|---|---|
| 호출자가 원하는 사용자의 캐시를 직접 지울 때 | 상품 수정 한 번으로 다음 조회가 새 가격을 사용해야 할 때 | 같은 상품의 요청은 기다릴 수 있고, 상품별 락은 API 프로세스 하나 안에서만 공유됨 |
