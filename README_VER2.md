# Mini Redis · 동시성과 캐시 무효화

저희 조는 AI를 활용해 Mini Redis를 각각 구현한 뒤, 완성된 두 코드를 비교해 현재 코드를 최종안으로 채택했습니다. 정글 가이드라인의 **동시성**과 **무효화**를 기준으로 각 설계에서 얻는 점과 감수할 비용을 살펴봤습니다.

| 순서 | 비교 기준 |
|---|---|
| [1. 동시성](#concurrency) | 여러 요청이 같은 저장소를 쓸 때, 누가 어떤 작업을 기다리는가 |
| [2. 무효화](#invalidation) | 원본이 바뀐 뒤, 이전 캐시를 누가 어떻게 무효화하는가 |
| [3. 선택 이유](#selection) | 팀이 감수한 비용과 최종 채택 기준 |

<a id="concurrency"></a>

## 1. 동시성 · 여러 요청이 공유 저장소를 쓰는 구조

**공통점** · 두 코드 모두 저장소 연산은 한 번에 하나씩 처리합니다. 긴 저장소 연산 뒤에 짧은 조회가 들어오면 둘 다 기다릴 수 있습니다.

| 설계 선택 | 얻는 점 | 감수하는 비용 |
|---|---|---|
| **현재 코드 · 멀티 스레드** | 연결마다 담당 스레드가 있어 저장소 락(`RLock`) 밖에서는 각자 요청을 읽고 응답을 보냄 | 요청을 보내지 않고 연결만 유지하는 클라이언트에도 스레드 하나가 필요 |
| **비교 코드 · 단일 스레드** | 한 스레드가 입력이 준비된 연결을 골라 명령을 처리하므로 연결마다 스레드를 만들거나 저장소 락을 잡을 필요가 없음 | 긴 명령을 실행하는 동안 다른 연결에서 이미 도착한 요청을 읽는 일도 미뤄짐 |

<a id="invalidation"></a>

## 2. 무효화 · 다음 조회에서 예전 값을 쓰지 않는 방법

| 설계 선택 | 얻는 점 | 감수하는 비용 |
|---|---|---|
| **현재 코드** · `PUT /products/1`에서 원본과 캐시 버전을 함께 변경 | 호출자는 수정 요청만 보냄. 예전 키 삭제가 실패해도 다음 조회는 새 키를 사용 | 같은 상품의 캐시 조회가 원본 응답을 기다리는 동안 수정도 대기. 상품별 락은 API 한 프로세스 안에서만 공유 |
| **비교 코드** · `DELETE /users/1`로 특정 캐시를 직접 삭제 | 호출자가 대상과 시점을 정할 수 있고, 진행 중인 원본 조회가 끝나기 전에 삭제 요청을 마칠 수 있음 | 삭제 시점을 호출자가 챙겨야 함. 먼저 시작한 조회가 삭제 뒤 같은 키를 다시 채울 수 있음 |

<a id="selection"></a>

## 3. 현재 코드를 선택한 이유

**원본을 수정하는 쪽에서 캐시 삭제까지 따로 챙길 필요가 없다는 점을 가장 중요하게 봤습니다.**

| 선택 기준 | 팀의 판단 |
|---|---|
| **동시성** | 현재 코드는 연결마다 스레드가 필요하고, 비교 코드는 긴 명령 하나가 다른 연결의 요청 처리를 늦출 수 있음. 이 차이만으로는 어느 한쪽을 고르기 어려웠음 |
| **무효화** | 같은 상품의 조회와 수정이 겹치면 한쪽이 기다림. 그 비용을 감수해도 수정 요청 하나로 다음 조회가 새 버전 키를 쓰도록 한 점을 우선함 |
