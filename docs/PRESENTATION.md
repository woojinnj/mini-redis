## 1. 무엇을 만들었나 · 0:00–0:30

> 화면 안내: 구조 그림을 짚고, 다음에는 동시성과 만료 두 주제를 설명한다고 안내합니다.

안녕하세요. 직접 만든 해시 테이블을 기반으로 구현한 미니 레디스를 소개하겠습니다.

외부 요청은 TCP 서버로 들어오고, 명령을 해석한 뒤 공유 저장소에 접근합니다. 해시 충돌은 연결 리스트로 처리했습니다.

과제의 다섯 중점 항목 중, 오늘은 저장소 내부 설계인 동시성과 만료 처리에 집중하겠습니다. 다른 구현과 비교하면서 우리 구조의 선택 이유와 한계도 설명하겠습니다.

## 2. 동시성: 저장소를 변경하는 순서를 보호한다 · 0:30–1:55

> 화면 안내: 먼저 구조 비교표, 이후 증가 예시를 보여줍니다. 락은 “공유 데이터에 들어가는 잠금장치”로 설명합니다.

먼저 동시성입니다. 두 요청이 숫자 0을 각각 읽고, 1씩 더해 저장한다고 생각해 보겠습니다. 두 요청 모두 1을 저장하면 결과는 2가 아닌 1입니다. 읽기와 저장 사이에 다른 요청이 끼어들었기 때문입니다.

비교 구현은 하나의 스레드가 여러 연결을 관리하는 이벤트 루프 방식입니다. 명령을 하나씩 끝까지 실행하므로 저장소 락이 필요 없습니다. 다만 오래 걸리는 명령이 있으면 다른 요청도 기다립니다.

우리는 연결마다 스레드가 요청을 처리하고, 모든 스레드가 하나의 저장소를 공유합니다. 따라서 저장소에 들어갈 때는 공통된 잠금장치인 락을 사용합니다.

숫자를 증가시키는 INCR 명령은 읽기부터 증가, 저장까지 락 안에서 처리합니다. 첫 요청이 1을 저장하고 락을 풀어야 다음 요청이 들어가므로, 다음 요청은 1을 읽고 2를 저장합니다.

이 구조에서는 요청 처리와 데이터 보호를 나눠 구현할 수 있습니다. 다만 저장소 연산은 전역 락 때문에 순차 실행됩니다. 스레드가 많다고 저장소 처리도 병렬로 빨라지는 것은 아닙니다.

보장 범위도 개별 명령입니다. 클라이언트가 GET과 SET을 따로 보내는 과정 전체까지 원자적으로 보장하지는 않습니다.

## 3. 만료: 응답의 유효성과 메모리 회수 · 1:55–2:55

> 화면 안내: 두 가지 처리 방식을 짚은 뒤, “GET도 삭제할 수 있다”는 문장을 강조합니다.

이제 같은 저장소에서 데이터의 수명을 어떻게 관리하는지 보겠습니다.

10초 동안만 보관할 값을 11초 뒤에 요청하면, 그 값은 없는 것으로 응답해야 합니다. 그래서 각 키에 만료 시각을 저장하고, 접근할 때 이미 만료됐다면 삭제합니다.

그런데 조회할 때만 지우면, 다시 조회되지 않는 키는 메모리에 남습니다. 이를 회수하기 위해 배경 스레드가 주기적으로 버킷을 순회합니다.

반대로 주기적 정리만 하면, 정리 작업이 방문하기 전에 만료된 값을 반환할 수 있습니다. 그래서 요청 시 확인과 주기적 정리를 함께 사용합니다. 비교 구현도 이 두 방법을 사용합니다.

여기서 앞의 동시성과 연결됩니다. GET도 만료된 키를 삭제할 수 있으므로 락이 필요하고, 배경 정리도 같은 락을 사용합니다.

따라서 만료 값의 반환을 막으면서, 사용자 요청과 배경 삭제가 저장소를 동시에 변경하는 문제도 방지합니다.

## 4. 외부 사용과 데이터 수명 · 2:55–3:35

> 화면 안내: 표의 세 행을 위에서 아래로 짚습니다. 상품별 락이 Redis 서버의 전역 락과 별개임을 구분합니다.

이 저장소를 외부에서 사용하는 구조도 만들었습니다. TCP의 RESP 프로토콜로 명령을 받고, HTTP 상품 API에서 캐시로 활용합니다.

무효화에는 DEL을 제공하며, 상품 API에는 별도의 상품별 락과 버전 키를 사용합니다. 상품 수정 후에는 새 버전 키를 읽으므로, 이전 캐시 삭제가 실패해도 옛 키를 재사용하지 않습니다. 이 보장은 API 한 프로세스 범위입니다.

데이터 보존은 스냅샷으로 구현했습니다. 저장된 상태는 복구하지만, 마지막 저장 이후의 변경은 강제 종료 시 잃을 수 있습니다.

## 5. 왜 이 구현을 선택하는가 · 3:35–4:00

> 화면 안내: 선택 이유를 먼저 말하고 검증 표를 짚습니다. 4분이 가까우면 마지막 문장을 서두르지 말고 아래 축약 지침을 적용합니다.

이 구현을 선택한 이유는 저장소의 명령 보호와 만료 처리를, 실제 API의 캐시 갱신까지 연결해 설명할 수 있기 때문입니다.

동시 증가, 만료 경계, 저장 후 복구 등을 포함한 30개 테스트로 동작을 확인했습니다.

전역 락의 병목과 마지막 스냅샷 이후 데이터 유실 가능성은 남아 있습니다. 이런 보장 범위와 한계를 구분한 구현입니다. 감사합니다.

- **1분 55초까지 동시성을 끝냅니다.** 처음 듣는 사람에게 원자성은 “작업 중간에 다른 요청이 끼어들지 않는 것”이라고 풀어 설명합니다.
- **2분 55초까지 만료를 끝냅니다.** 앞부분이 길어지면 2번의 “이 구조에서는 요청 처리와 데이터 보호를 나눠 구현할 수 있습니다.”와 3번의 “비교 구현도 이 두 방법을 사용합니다.”를 생략할 수 있습니다.
- **3분 35초에 선택 이유로 넘어갑니다.** 4번이 길어지면 “무효화는 DEL과 상품 API의 버전 키로 처리하고, 스냅샷으로 저장된 상태를 복구합니다. 다만 마지막 저장 이후 변경은 유실될 수 있습니다.”로 압축합니다.
- 테스트 30개는 특정 시나리오를 검증한 결과입니다. “동시성 문제가 절대 없다”, “상대보다 빠르다”, “장애에도 데이터가 전부 남는다”고 표현하지 않습니다.
- 이 대본은 현재 구현의 선택 근거를 설명합니다. 실제 개발 순서나 당시 고민을 확인 없이 “처음부터 비교해서 이렇게 설계했다”고 덧붙이지 않습니다.
- `RLock`은 “알 락”, `INCR`는 “증가 명령”, `RESP`는 “레스프 프로토콜”처럼 편한 표현으로 읽어도 됩니다.
- 100ms와 32개 버킷은 화면의 구현 정보입니다. 본문 낭독에서는 숫자를 추가로 설명하지 않아도 됩니다.

## 예상 질문과 답변 · 발표 시간에 포함하지 않음

### 왜 일반 Lock 대신 RLock을 사용했나요?

같은 스레드가 이미 가진 락을 다시 획득할 수 있어야 하는 호출 경로가 있습니다.
`dbsize()`가 락을 잡은 상태에서, 내부적으로 다시 락을 사용하는 `sweep()`를 호출합니다.
현재 구조에서 일반 Lock으로 단순 교체하면 자기 자신이 가진 락을 기다리게 됩니다.
RLock이 여러 스레드의 동시 접근을 허용하는 것은 아닙니다.

근거: [Store의 dbsize와 sweep](../mini_redis/store.py)

### 동시성만 보면 우리 방식이 더 좋은가요?

그렇게 단정할 수 없습니다. 상대의 단일 이벤트 루프도 명령 원자성을 제공하고, 저장소 락 관리가 필요 없다는 장점이 있습니다.
우리는 연결별 요청 흐름을 순서대로 작성하고 Store에 데이터 보호를 모았습니다.
그 대신 스레드 비용과 전역 락의 병목을 감수합니다. 같은 조건의 성능 비교 없이는 빠르다고 말할 수 없습니다.

### 상품별 락과 저장소 락은 무엇이 다른가요?

저장소 락은 개별 Redis 명령을 보호합니다.
상품별 락은 API에서 같은 상품의 캐시 조회·원본 조회·캐시 저장과 상품 수정을 조정합니다.
서로 다른 상품의 API 작업은 별도로 진행할 수 있지만 Redis 저장소 연산은 전역 락을 따릅니다.
이 락들은 각 프로세스 내부의 장치이며 여러 API 서버에 자동으로 공유되지 않습니다.

근거: [Catalog.get과 update](../mini_redis/demo.py)

### 100ms마다 모든 만료 키가 삭제되나요?

아닙니다. 배경 작업이 100ms를 기다린 뒤 최대 32개 버킷을 확인합니다.
전체 버킷 수, 락 대기, 각 버킷의 키 수에 따라 실제 회수 시점은 달라집니다.
아직 정리되지 않은 키라도 요청이 오면 만료를 확인하므로 만료된 값으로 응답하지 않도록 합니다.
절대 시각을 사용하므로 시스템 시계 변경의 영향도 받습니다.

### 왜 AOF 대신 스냅샷인가요?

현재 구현의 보존 범위는 저장 시점의 상태 복구입니다.
락 안에서 일관된 복사본을 만들고, 임시 파일에 기록한 뒤 원자적으로 교체하는 방식을 구현했습니다.
변경을 계속 기록하는 AOF는 구현하지 않았으므로 최신 쓰기 보존에서는 한계가 있습니다.
AOF보다 더 안전해서 선택했다고 주장하지 않습니다.

근거: [Store.save와 load](../mini_redis/store.py)

### 테스트는 무엇을 확인했나요?

Store에서 16개 작업자가 각각 1,000회 증가시켜 총 16,000인지 확인하고,
실제 TCP 동시 증가도 별도로 검증합니다. 가짜 시계로 만료 경계와 정리를 확인합니다.
상품 API에서는 동시 캐시 미스, 수정 후 무효화, Redis 장애 시 원본 조회를 검사합니다.
복구 테스트는 SAVE 후 프로세스를 강제 종료해 저장된 값은 복구되고 저장 이후 값은 사라지는 것까지 확인합니다.

근거: [저장소 테스트](../tests/test_store.py) · [통신·API 테스트](../tests/test_network.py) · [재시작 테스트](../tests/test_lifecycle.py)

### 기존 성능 측정 결과는 왜 발표에서 다루지 않나요?

4분 발표는 동시성과 만료의 설계에 집중합니다.
기존 벤치마크는 인위적 원본 지연을 두고 캐시 사용 효과를 측정한 것이며, 비교 프로젝트와의 속도 대결이 아닙니다.
측정 환경과 원본 지연, 미스 준비 비용 등은 [상세 문서](REFERENCE.md)의 테스트와 성능 측정 부분에 남겼습니다.
