## 2. 동시성: 저장소를 변경하는 순서를 보호한다 · 0:30–1:55

### 구조 비교 · 0:30–1:10

> 화면: [같은 목표, 다른 구조](../README.md#concurrency-models)
>
> 짚는 순서: “비교 구현 · C”의 이벤트 루프 → “우리 구현 · Python”의 공유 RLock.
> 두 경로를 설명한 뒤 바로 아래 비교표의 장점·비용 행을 짚습니다.
> 아래쪽 증가 예시는 아직 설명하지 않습니다.

이 구조에서 첫 번째로 살펴볼 것은 **동시성**입니다. 화면의 **같은 목표, 다른 구조**처럼, 두 구현 모두 한 명령이 저장소를 변경하는 중간에 다른 명령이 끼어들지 않게 합니다.

비교 구현은 그림의 **하나의 이벤트 루프**가 여러 연결을 관리하며 명령을 순서대로 실행합니다.

우리는 연결별 스레드가 요청을 받고, 그림의 **공유 RLock**, 즉 잠금장치를 거쳐 저장소에 접근합니다.

아래 표처럼 상대는 저장소 락 관리가 필요 없고, 우리는 요청 처리와 저장소 보호를 나눠 구현합니다. 대신 상대는 긴 작업이 이벤트 루프를 지연시키고, 우리는 스레드 비용과 락 대기를 감수합니다. 두 방식 모두 저장소 연산은 순차 실행됩니다.

### 증가 예시와 보장 범위 · 1:10–1:55

> 화면: [두 번 증가시켰는데 결과가 1이라면?](../README.md#atomic-increment)
>
> 짚는 순서: 초깃값 0 → 왼쪽 열을 위에서 아래로 → 오른쪽 열을 위에서 아래로.
> 마지막에 “보장 범위” 인용문을 보여줍니다. 구조 그림으로 다시 올라가지 않습니다.

이 차이가 실제 값에 어떤 영향을 주는지, 아래 증가 예시로 보겠습니다.

초깃값은 0입니다. **왼쪽 열**처럼 두 요청이 모두 0을 읽은 뒤 각각 1을 저장하면, 두 번 증가시켜도 **결과는 1**입니다.

**오른쪽의 INCR**는 읽기부터 증가, 저장까지 락 안에서 실행합니다. A가 1을 저장하고 락을 풀면, 기다리던 B가 1을 읽고 2를 저장합니다. 그래서 **결과는 2**입니다.

맨 아래처럼 보장 범위는 **단일 프로세스의 개별 명령**입니다. 클라이언트가 GET과 SET을 따로 보내는 과정 전체를 잠그지는 않습니다. 또한 전역 락을 사용하므로, 스레드가 많다고 저장소 처리도 병렬로 빨라지지는 않습니다.

## 3. 만료: 값의 유효성과 메모리 회수 · 1:55–2:55

### 만료 판단과 회수 · 1:55–2:35

> 화면: [3. 만료: 값의 유효성과 메모리 회수](../README.md#expiration)
>
> 짚는 순서: 만료 조건 → 흐름도의 GET 요청 → 만료 판단 → 삭제 → null 반환.
> 이어서 “배경 정리” 경로를 짚고, 아래 표의 두 행을 설명합니다.

지금까지는 데이터를 **어떤 순서로 바꾸는지** 봤습니다. 다음은 그 데이터를 **언제까지 유효하게 볼지**입니다.

맨 위 조건처럼 현재 시각이 만료 시각에 도달하면 없는 키로 취급합니다. 흐름도에서 GET 요청이 들어오면 만료 여부를 확인하고, 만료됐다면 **삭제 후 null**을 반환합니다.

하지만 조회할 때만 지우면 다시 조회되지 않는 키가 남습니다. 그래서 그림의 **배경 정리**가 버킷을 순회하며 회수합니다.

아래 표의 두 행을 함께 쓰는 이유입니다. 접근 시 확인은 만료된 값의 반환을 막고, 주기적 정리는 사용하지 않는 데이터의 메모리를 회수합니다.

### 앞의 동시성과 연결 · 2:35–2:55

> 화면: [GET도 데이터를 삭제할 수 있다](../README.md#expiry-lock)
>
> 강조 문구를 먼저 짚고, 바로 아래 공통점·차이 표를 보여줍니다.

여기서 강조한 문장이 **GET도 데이터를 삭제할 수 있다**입니다. 그래서 조회와 배경 정리도 앞서 설명한 같은 저장소 락을 사용합니다.

아래 표처럼 상대도 두 만료 처리 방식을 함께 씁니다. 차이는 상대가 이벤트 루프에서 정리하고, 우리는 별도 배경 스레드가 공유 락을 사용한다는 점입니다.

## 4. 외부 사용과 데이터 수명 · 2:55–3:35

> 화면: [4. 외부 사용과 데이터 수명](../README.md#external-use)
>
> 짚는 순서: 첫 표의 외부 API → 무효화 → 데이터 보존, 이후 “두 락의 역할” 표.
> 보존을 말한 뒤 무효화 표로 돌아가지 않고, 두 락의 차이로 연결합니다.

이제 이 저장소를 외부에서 사용하는 방법입니다. 표의 **왼쪽**은 TCP 명령과 HTTP 상품 API를 통한 캐시 사용입니다.

**가운데 무효화**는 상품 수정 후 버전을 바꾸고 이전 키를 삭제합니다. 다음 조회는 **새 버전 키**를 읽어 옛 캐시를 재사용하지 않습니다.

**오른쪽 데이터 보존**은 스냅샷입니다. 저장된 상태는 복구하지만 **마지막 저장 이후 변경은 유실될 수 있습니다.**

아래 **두 락의 역할**도 구분했습니다. 저장소 락은 개별 명령을, 상품별 락은 같은 상품의 캐시 조회와 수정을 조정합니다. 상품 원본은 메모리 예제이며, API의 보장은 한 프로세스 범위입니다.

## 예상 질문과 답변 · 발표 시간에 포함하지 않음

### 왜 일반 Lock 대신 RLock을 사용했나요?

같은 스레드가 이미 가진 락을 다시 획득할 수 있어야 하는 호출 경로가 있습니다.
`dbsize()`가 락을 잡은 상태에서, 내부적으로 다시 락을 사용하는 `sweep()`를 호출합니다.
현재 구조에서 일반 Lock으로 단순 교체하면 자기 자신이 가진 락을 기다리게 됩니다.
RLock이 여러 스레드의 동시 접근을 허용하는 것은 아닙니다.

근거: [Store의 dbsize와 sweep](../mini_redis/store.py)

### 동시성만 보면 우리 방식이 더 좋은가요?

그렇게 단정할 수 없습니다. 상대의 단일 이벤트 루프도 명령 원자성을 제공하고, 저장소 락 관리가 필요 없다는 장점이 있습니다.
우리는 연결별 요청 흐름을 순서대로 작성하고 Store에 데이터 보호를 모았습니다.
그 대신 스레드 비용과 전역 락의 병목을 감수합니다. 같은 조건의 성능 비교 없이는 빠르다고 말할 수 없습니다.

### 상품별 락과 저장소 락은 무엇이 다른가요?

저장소 락은 개별 Redis 명령을 보호합니다.
상품별 락은 API에서 같은 상품의 캐시 조회·원본 조회·캐시 저장과 상품 수정을 조정합니다.
서로 다른 상품의 API 작업은 별도로 진행할 수 있지만 Redis 저장소 연산은 전역 락을 따릅니다.
이 락들은 각 프로세스 내부의 장치이며 여러 API 서버에 자동으로 공유되지 않습니다.

근거: [Catalog.get과 update](../mini_redis/demo.py)

### 100ms마다 모든 만료 키가 삭제되나요?

아닙니다. 배경 작업이 100ms를 기다린 뒤 최대 32개 버킷을 확인합니다.
전체 버킷 수, 락 대기, 각 버킷의 키 수에 따라 실제 회수 시점은 달라집니다.
아직 정리되지 않은 키라도 요청이 오면 만료를 확인하므로 만료된 값으로 응답하지 않도록 합니다.
절대 시각을 사용하므로 시스템 시계 변경의 영향도 받습니다.

### 왜 AOF 대신 스냅샷인가요?

현재 구현의 보존 범위는 저장 시점의 상태 복구입니다.
락 안에서 일관된 복사본을 만들고, 임시 파일에 기록한 뒤 원자적으로 교체하는 방식을 구현했습니다.
변경을 계속 기록하는 AOF는 구현하지 않았으므로 최신 쓰기 보존에서는 한계가 있습니다.
AOF보다 더 안전해서 선택했다고 주장하지 않습니다.

근거: [Store.save와 load](../mini_redis/store.py)

### 테스트는 무엇을 확인했나요?

Store에서 16개 작업자가 각각 1,000회 증가시켜 총 16,000인지 확인하고,
실제 TCP 동시 증가도 별도로 검증합니다. 가짜 시계로 만료 경계와 정리를 확인합니다.
상품 API에서는 동시 캐시 미스, 수정 후 무효화, Redis 장애 시 원본 조회를 검사합니다.
복구 테스트는 SAVE 후 프로세스를 강제 종료해 저장된 값은 복구되고 저장 이후 값은 사라지는 것까지 확인합니다.

근거: [저장소 테스트](../tests/test_store.py) · [통신·API 테스트](../tests/test_network.py) · [재시작 테스트](../tests/test_lifecycle.py)

### 기존 성능 측정 결과는 왜 발표에서 다루지 않나요?

4분 발표는 동시성과 만료의 설계에 집중합니다.
기존 벤치마크는 인위적 원본 지연을 두고 캐시 사용 효과를 측정한 것이며, 비교 프로젝트와의 속도 대결이 아닙니다.
측정 환경과 원본 지연, 미스 준비 비용 등은 [상세 문서](REFERENCE.md)의 테스트와 성능 측정 부분에 남겼습니다.
