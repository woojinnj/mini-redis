## 도입과 전체 구조 · 0:00–0:35

> 화면: [비교 순서](../README.md#roadmap) → [전체 구조](../README.md#overview)
>
> 다섯 항목을 미리 짚은 뒤 구조 그림으로 내려갑니다. 구조 설명에서는 현재 구현만 설명합니다.

저희 조는 AI로 개발을 마친 뒤, 서로의 구현이 어떻게 다른지 비교했습니다. 기준은 **정글 가이드라인의 다섯 중점 사항**입니다.

먼저 전체 구조를 보고, **동시성, 만료 처리, 외부 API, 무효화, 서버 장애 시 보존**을 차례로 비교하겠습니다. 각 항목의 구현 방식과 장단점을 살펴본 뒤, 최종 선택 이유를 말씀드리겠습니다.

현재 구현은 그림처럼 TCP로 받은 RESP2 명령을 연결별 스레드가 해석합니다. 이후 RLock으로 접근을 조정하는 **공유 Store**를 거쳐, 직접 만든 해시 테이블을 조회하거나 수정합니다.

## 1. 동시성 · 0:35–1:15

> 화면: [1. 동시성](../README.md#concurrency)
>
> 문제 문장 → 도식의 현재 경로 → 팀원 경로 → 표의 장점·비용 → “개별 명령” 문구 순서입니다.
> 만료 정리나 상품별 락은 해당 항목에서 설명하므로 여기서는 개별 저장소 명령에 집중합니다.

첫째는 **동시성**입니다. 여러 요청의 저장소 연산이 서로 끼어들지 않게 하는 것이 목표입니다.

현재 구현은 연결별 스레드가 요청을 처리하고, **공유 RLock**으로 저장소에는 한 번에 하나씩 접근합니다. 팀원 구현은 **단일 이벤트 루프**가 여러 연결의 명령을 순서대로 실행합니다.

표처럼 현재 구조는 요청 처리와 저장소 보호를 분리하지만, 스레드 비용과 락 경합이 있습니다. 팀원 구조는 저장소 락과 연결별 스레드가 필요 없지만, 긴 작업이 이벤트 루프를 지연시킵니다.

**둘 다 개별 명령을 보호합니다.** 현재 구현도 저장소 연산은 순차 실행되므로, 멀티스레드라는 이유로 더 빠르다고 볼 수는 없습니다.

## 2. 만료 처리 · 1:15–1:55

> 화면: [2. 만료 처리](../README.md#expiration)
>
> 도식의 “접근 시 확인 · 지연 삭제” 경로 → “주기적 정리 · 능동 삭제” 경로 → 공통 규칙 → 비교표 순서입니다.
> “현재 시각 ≥ 만료 시각”의 경계는 “도달하면”으로 읽습니다.

둘째는 **만료 처리**입니다. 만료된 값의 반환을 막으면서 메모리도 회수해야 합니다.

**두 구현 모두 같은 두 방법을 사용합니다.** 접근 시 확인하는 **지연 삭제**는 만료 시각에 도달한 키를 삭제하고 null을 반환합니다. **능동 삭제**는 주기적으로 버킷을 순회해 조회되지 않는 만료 키도 지웁니다.

표처럼 현재는 배경 스레드와 공유 락을, 팀원은 이벤트 루프를 사용합니다. 둘 다 만료 응답 방지와 메모리 회수라는 장점이 있지만, 정리하는 동안 현재는 락을, 팀원은 이벤트 루프를 점유합니다.

지연 삭제만 쓰면 미조회 키가 남고, 능동 삭제만 쓰면 정리 전 요청에서 만료를 놓칠 수 있어 두 방법을 함께 씁니다.

## 3. 외부 API · 1:55–2:20

> 화면: [3. 외부 API](../README.md#external-api)
>
> 현재·팀원 접근 경로와 양쪽 HTTP 예제를 짚은 뒤 비교표로 내려갑니다.
> 여기서는 연결과 사용 편의성만 설명합니다. 수정 시 캐시 삭제와 장애 시 복구는 다음 항목으로 남깁니다.

셋째는 **외부 API**입니다. 다른 프로그램이 쉽게 사용할 수 있어야 합니다.

두 구현 모두 **TCP의 RESP 명령과 HTTP 예제 API**를 제공합니다. 현재는 CLI와 GUI로 호출과 결과를 확인하기 쉽고, 팀원은 지원 명령이 더 넓고 연결 풀로 연결을 재사용합니다.

비용도 다릅니다. 현재 Python 클라이언트는 명령마다 연결을 만들고, 팀원은 풀의 연결 반환과 오류 처리를 관리해야 합니다.

## 4. 무효화 · 2:20–3:00

> 화면: [4. 무효화](../README.md#invalidation)
>
> 현재의 수정 → 새 버전 키, 팀원의 DELETE → 재생성 경로를 짚습니다.
> 비교표의 장점·한계를 설명한 뒤 맨 아래 “두 락의 역할” 표로 내려갑니다.
> 스냅샷은 다음 5번에서 처음 설명합니다.

넷째는 **무효화**입니다. 원본이 바뀌면 이전 캐시를 다시 사용하지 않아야 합니다.

현재 상품 API는 **상품별 락 안에서 버전을 올리고 이전 키를 삭제**합니다. 팀원은 HTTP DELETE와 전체 삭제 명령으로 캐시를 지웁니다.

현재는 삭제에 실패해도 새 버전 키를 사용한다는 장점이 있고, 팀원은 명시적 삭제와 일괄 삭제가 가능합니다.

한계는 현재의 락 대기와 API 한 프로세스 범위입니다. 팀원은 진행 중인 조회가 삭제 뒤 같은 키를 다시 채우는 상황을 조정하지 않습니다.

아래 표처럼 **저장소 락은 개별 명령**, **상품별 락은 조회·캐시 채우기·수정 과정**을 보호합니다.

## 5. 서버 장애 시 데이터 보존 · 3:00–3:35

> 화면: [5. 서버 장애 시 데이터 보존](../README.md#persistence)
>
> 현재 스냅샷 경로 → 팀원 AOF 경로 → 표의 장점 → 마지막 저장 이후 유실과 기록 비용을 짚습니다.
> 서버가 꺼진 뒤 복구하는 이야기입니다. “Redis가 죽어도 HTTP API가 원본으로 응답한다”는 가용성 설명과 섞지 않습니다.

마지막 다섯째는 **서버 장애 시 데이터 보존**입니다. 갑자기 종료된 뒤 무엇을 복구할 수 있는지 봤습니다.

현재는 SAVE나 정상 종료 때 **스냅샷**을 저장하고 시작할 때 읽습니다. 팀원은 변경 명령을 **AOF**에 계속 기록하고 재실행합니다.

현재는 일관된 복사본과 원자적 파일 교체로 저장하고, 팀원은 지속적인 기록과 동기화 정책 선택이 장점입니다.

다만 현재는 **마지막 저장 이후 변경을 잃을 수 있습니다.** 팀원은 기록 비용이 있고, 쓰기 실패에도 성공으로 응답할 수 있습니다. 복구 범위와 비용이 다른 선택입니다.

팀원의 명령 범위와 AOF의 장점은 인정하며, 현재의 전역 락 병목과 저장 이후 유실 가능성은 개선 과제입니다. 현재 구현은 **30개 테스트**로 동작을 확인했습니다. 감사합니다.

## 리허설 메모 · 읽지 않음

- 도입에서 다섯 항목을 모두 예고합니다. README의 1~5번과 대본의 1~5번은 같은 항목입니다.
- 매번 **문제 → 현재·팀원 구현 → 장점·한계** 순서로 설명합니다. “비교 핵심”은 그 항목의 결론이며, 전체 선택 이유는 맨 마지막에 말합니다.
- 1번은 서버 내부 명령, 3번은 호출 경로, 4번은 캐시 갱신, 5번은 종료 후 복구에 집중합니다. 상품별 락은 4번, 스냅샷은 5번에서 설명합니다.
- 표의 모든 내용을 읽을 필요는 없습니다. 굵은 문구를 짚고 본문대로 말하면 각 항목의 차이와 장단점을 전달할 수 있습니다.
- 4분은 목표입니다. 실제로 읽고 스크롤하면서 시간을 확인하세요. 긴장해서 빨리 읽기보다 아래 문장을 생략하는 편이 좋습니다.
- 시간이 부족하면 1번 마지막의 “현재 구현도 저장소 연산은…”과 2번 마지막의 “지연 삭제만 쓰면…”을 생략할 수 있습니다. 표에는 한계와 두 방법의 필요성이 남아 있습니다.
- 5번의 마지막 저장 이후 유실 가능성과, 4번의 API 한 프로세스 범위는 생략하지 않습니다.
- “팀원 구현은 락이 전혀 없다” 대신 “Redis 저장소 락이 필요 없다”고 말합니다. 팀원 Python 연결 풀에는 별도 락이 있습니다.
- 두 API의 원본은 실제 DB를 연동한 운영 서비스가 아닌 예제입니다.
- `RLock`은 “알 락”, `INCR`는 “증가 명령”, `RESP`는 “레스프”, `AOF`는 “에이오에프”로 읽어도 됩니다.
- 구현 비교는 README에 명시한 고정 커밋 기준입니다. 성능 우열, 무손실 복구, 모든 동시성 상황의 안전성을 주장하지 않습니다.

## 예상 질문과 답변 · 발표 시간에 포함하지 않음

### 왜 현재 구현이 더 빠르다고 말하지 않나요?

저장소 연산은 두 구현 모두 순차 실행합니다. 요청 처리 방식이 다르다는 사실만으로 처리량을 결정할 수 없습니다.
같은 조건의 두 프로젝트 성능 비교는 수행하지 않았습니다.
기존 벤치마크는 인위적 원본 지연을 두고 캐시 사용 효과를 측정한 것이며 조건은 [상세 문서](REFERENCE.md)에 남겼습니다.

### 왜 일반 Lock 대신 RLock을 사용했나요?

현재 `dbsize()`는 락을 잡은 상태에서 다시 락을 사용하는 `sweep()`를 호출합니다.
RLock은 같은 스레드가 자신이 가진 락을 다시 획득할 수 있게 합니다.
여러 스레드가 동시에 저장소에 들어갈 수 있게 하는 장치는 아닙니다.

근거: [Store의 dbsize와 sweep](../mini_redis/store.py)

### GET과 SET도 안전하다면 두 명령으로 증가시켜도 되나요?

각 명령은 보호하지만, GET으로 읽은 뒤 SET을 보내기 전에 다른 명령이 끼어들 수 있습니다.
현재의 INCR는 조회·검증·증가·저장을 한 락 안에서 실행합니다.
팀원도 INCR 전체를 이벤트 루프에서 실행합니다. 둘 다 여러 명령 전체를 트랜잭션으로 묶는 보장은 없습니다.

### 왜 GET과 만료 정리에도 락이 필요한가요?

GET은 만료된 키를 발견하면 삭제합니다. 읽기처럼 보이지만 저장소를 변경할 수 있습니다.
사용자 요청의 수정·삭제·리사이징과 배경 정리가 경쟁하지 않도록 같은 저장소 락을 사용합니다.

### 주기 정리는 즉시 모든 만료 키를 없애나요?

아닙니다. 현재는 100ms를 기다린 뒤 최대 32개 버킷을, 팀원은 이벤트 루프의 주기 작업에서 최대 1,000개 버킷을 확인합니다.
한 버킷의 키 수, 전체 버킷 수, 다른 작업의 지연에 따라 회수 시점이 달라집니다.
양쪽 모두 절대 시각을 쓰므로 시스템 시계 변경의 영향도 받습니다.

### 상품별 락과 버전 키는 각각 왜 필요한가요?

상품별 락은 같은 상품의 캐시 조회·원본 조회·캐시 저장과 수정이 엇갈리지 않도록 합니다.
버전 키는 수정 후 이전 캐시 삭제가 실패해도 다음 조회가 옛 키를 읽지 않게 합니다.
남아 있는 옛 키는 TTL로 회수합니다. 이 전략은 해당 API 한 프로세스 범위입니다.

근거: [Catalog.get과 update](../mini_redis/demo.py)

### 팀원도 DEL이 있는데 무효화에서 무슨 차이가 있나요?

DEL 한 명령의 안전성과 API 전체 작업의 순서 보장은 다릅니다.
팀원 HTTP 데모는 조회 중 원본을 가져오는 동안 DELETE가 완료되면, 뒤늦은 조회가 같은 키를 다시 채울 수 있습니다.
실제 원본 수정 API는 없으며, 변경 가능한 원본에 적용할 때는 오래된 값 재저장 문제를 추가로 다뤄야 합니다.

근거: [팀원 HTTP API](https://github.com/minseongkim275-dotcom/mini-redis/blob/bfb1c0566b00e2b30a03cb5b4c0845e357f0a0e0/demo/api_server.py)

### 스냅샷을 선택했으니 AOF보다 더 안전한가요?

그렇게 주장하지 않습니다. 현재는 저장 시점의 상태 복구를 구현했고, 마지막 저장 이후의 변경은 잃을 수 있습니다.
팀원 AOF는 지속적으로 변경을 기록한다는 장점이 있습니다. 다만 fsync 정책, 실제 디스크 오류, 명령 재생의 정확성까지 함께 평가해야 합니다.
현재 코드의 `SAVE`는 저장 실패를 오류로 전달하지만, 팀원 AOF의 기록 실패는 경고만 남기고 명령 성공 응답을 막지 않습니다.

근거: [현재 Store.save](../mini_redis/store.py) · [팀원 AOF](https://github.com/minseongkim275-dotcom/mini-redis/blob/bfb1c0566b00e2b30a03cb5b4c0845e357f0a0e0/src/aof/aof.c)

### 서버 장애 중 API 응답과 데이터 복구는 같은 이야기인가요?

아닙니다. 두 HTTP 데모 모두 캐시 조회 연결에 실패하면 원본을 조회해 응답하는 경로가 있습니다.
이는 API의 가용성에 관한 처리입니다. 스냅샷과 AOF는 서버가 다시 시작할 때 저장 데이터를 복구하는 영속성 기능입니다.
5번은 가이드라인의 데이터 보존 요구에 맞춰 영속성을 비교합니다.

### 30개 테스트는 무엇을 확인했나요?

Store에서 16개 작업자가 1,000회씩 증가한 결과 16,000과 실제 TCP 동시 증가를 확인합니다.
가짜 시계로 만료 경계와 정리를, HTTP로 캐시 미스·수정 후 무효화·장애 시 원본 조회를 검사합니다.
복구 테스트는 SAVE 후 프로세스를 강제 종료해 저장된 값은 복구되고 저장 이후 값은 사라지는 것까지 확인합니다.
특정 시나리오의 검증이며 모든 실행 순서나 운영 환경의 안전성을 증명하지는 않습니다.
