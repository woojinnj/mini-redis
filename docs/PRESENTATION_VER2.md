## 0:00–0:25 · 비교할 두 질문

> README 맨 위에서 ‘살펴볼 순서’의 두 질문을 짚는다.

저희 조는 AI로 각각 Mini Redis를 구현한 뒤 두 가지를 비교했습니다. 첫째, 두 사람이 같은 숫자를 동시에 올리면 둘 다 반영될까요? 둘째, 상품 가격을 바꾸면 다음 사람은 새 가격을 볼까요? 두 서버의 구조를 살펴보고, 두 번째 질문에서 저희의 선택 이유를 말씀드리겠습니다.

## 0:25–1:35 · 동시성

> [동시성](../README_VER2.md#concurrency)의 첫 표에서 두 구현을 왼쪽부터 비교하고, 둘째 표에서 최종값 2와 1을 짚는다.

먼저 숫자가 0이라고 해보겠습니다. 두 클라이언트가 각각 1을 더하면 우리가 기대하는 결과는 2입니다. Redis의 증가 명령인 INCR는 현재 값을 읽고, 1을 더하고, 다시 저장하는 일까지 한 번에 요청합니다.

왼쪽의 우리 서버는 연결마다 스레드가 있어서 여러 요청을 받을 수 있습니다. 대신 숫자를 바꿀 때는 공유 저장소에 락을 겁니다. A가 0을 읽고 1을 저장할 때까지 B가 기다리니, B는 1을 읽고 2를 저장합니다. 요청을 따로 받을 수 있지만, 락을 오래 잡으면 다른 키를 쓰려는 요청도 기다립니다.

오른쪽의 팀원 서버는 한 스레드가 여러 연결을 살피면서 명령을 하나씩 끝냅니다. 그래서 저장소 락 없이도 같은 결과가 나옵니다. 다만 긴 명령을 처리하는 동안에는 뒤의 명령도 기다립니다.

그런데 아래 표처럼 각자 GET으로 읽고, 직접 1을 더해서 SET으로 저장하면 어떨까요? A와 B가 둘 다 0을 읽고 나중에 둘 다 1을 쓸 수 있습니다. 두 서버 모두 개별 명령은 보호하지만, 명령과 명령 사이에는 다른 요청이 들어올 수 있습니다.

## 1:35–3:20 · 무효화

> [무효화](../README_VER2.md#invalidation)의 비교표에서 시작해, 팀원 예시는 순서표 ①~③을, 현재 예시는 ‘상품별 락’과 ‘버전 키’를 차례로 짚는다.

이 차이가 실제로 드러나는 곳이 캐시입니다. 상품 가격이 1,000원일 때 조회한 응답을 저장해 뒀다고 해보겠습니다. 가격을 1,200원으로 바꾼 뒤에도 그 응답을 그대로 돌려주면, 사용자는 여전히 1,000원을 봅니다. 이때 예전 응답을 다시 쓰지 않게 하는 게 무효화입니다.

먼저 팀원 데모의 예시는 사용자 정보입니다. 호출자가 사용자 한 명의 캐시를 지워 달라고 하면 API가 해당 키를 삭제합니다. 원하는 캐시를 직접 지정해서 지울 수 있습니다. 그런데 표처럼 조회와 삭제가 겹치면 어떻게 될까요?

①에서 A는 캐시가 비어 있어서 원본을 읽으러 갑니다. 그사이 ②에서 B의 삭제 요청이 끝납니다. 그런데 ③에서 A가 원본 응답을 받아 같은 키에 저장합니다. 그러면 삭제 요청이 끝난 뒤에 키가 다시 생깁니다. 앞에서 본 것처럼 GET, DEL, SET 각각이 순서대로 실행돼도 가능한 일입니다.

우리 상품 API는 원본 가격을 바꾸는 요청까지 다룹니다. 여기에는 두 장치가 있습니다. 먼저 **상품별 락**입니다. 같은 상품을 조회하는 쪽이 먼저 락을 잡았다면 캐시를 다 채운 뒤에 수정이 진행됩니다. 반대로 수정이 먼저라면 조회가 기다립니다. 앞에서 본 저장소 락보다 더 긴 작업, 즉 상품을 읽어서 캐시에 채우는 과정 전체의 순서를 맞춰 주는 겁니다.

두 번째는 **버전 키**입니다. 가격을 1,200원으로 바꾸면서 버전을 1에서 2로 올리고 예전 키를 삭제합니다. 여기서 삭제에 실패했다고 해도 다음 조회는 버전 2를 찾습니다. 버전 1에 남은 1,000원을 건네줄 일이 없는 이유입니다.

## 3:20–4:00 · 선택 이유

> [선택 이유](../README_VER2.md#selection)의 마지막 표에서 ‘선택한 기준’과 ‘한계’를 짚는다.

두 구현 모두 동시 증가를 처리할 수 있습니다. 저희의 선택을 가른 건 가격을 수정한 뒤의 첫 조회였습니다. 팀원 데모처럼 특정 캐시만 직접 지우는 기능도 유용합니다. 우리 상품 API에서는 가격을 바꾼 사람이 캐시 삭제까지 따로 챙길 필요가 없습니다.

물론 상품별 락을 쓰면 같은 상품의 요청이 기다리고, 이 보호는 API 한 프로세스 안에서만 적용됩니다. 그 범위에서 **상품 수정 한 번으로 다음 조회가 새 가격을 사용하도록 했다**는 점이 저희가 현재 구현을 선택한 이유입니다. 감사합니다.
