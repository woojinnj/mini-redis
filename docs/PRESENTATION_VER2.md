# Mini Redis · 4분 발표 대본 Ver2

[발표용 README](../README_VER2.md) · 인용문은 발표 중에 볼 위치입니다.

## 0:00–0:25 · 발표 순서

> README 첫 표에서 동시성, 무효화, 선택 이유를 차례로 짚는다.

저희 조는 AI로 Mini Redis를 각각 만든 뒤, 두 코드를 비교해서 현재 코드를 골랐습니다. 오늘은 그 이유를 말씀드리겠습니다. 먼저 **동시성**, 여러 요청이 겹칠 때 두 서버가 어떻게 처리하는지 보겠습니다. 다음은 **무효화**, 원본이 바뀌면 예전에 저장한 값을 어떻게 처리하는지입니다. 마지막으로 두 방식의 장단점 중에서 저희가 어떤 점을 더 중요하게 봤는지 말씀드리겠습니다.

## 0:25–1:35 · 동시성

> [동시성 표](../README_VER2.md#concurrency)에서 현재 코드와 비교 코드의 ‘좋은 점’과 ‘감수할 점’을 짚는다.

먼저 동시성입니다. 서버에서는 한 사람의 요청이 끝나기 전에 다른 사람의 요청이 들어올 수 있습니다. 두 코드 모두 저장소에서 값을 읽거나 바꾸는 일은 하나씩 처리합니다. 차이는 그동안 다음 요청을 누가 받아 주느냐에 있습니다.

현재 코드는 **멀티 스레드**입니다. 스레드는 프로그램 안에서 일을 처리하는 단위인데, 현재 코드는 연결마다 하나씩 둡니다. A가 저장소를 쓰는 동안에도 B를 맡은 스레드는 B가 보낸 요청을 미리 읽을 수 있습니다. 다만 B도 저장소를 써야 하면 A가 끝날 때까지 기다립니다. 이렇게 한 번에 하나의 스레드만 저장소를 쓰도록 하는 게 락입니다. 이 방식은 일을 나눠 맡을 수 있지만, 요청을 보내지 않고 연결만 해 둬도 담당 스레드가 하나 필요합니다.

비교 코드는 **단일 스레드**입니다. 스레드 하나가 여러 연결을 살피다가 요청이 들어온 곳을 골라 처리합니다. 그래서 연결이 늘어도 담당 스레드를 더 만들 필요가 없습니다. 대신 그 스레드가 A의 긴 명령을 처리하는 중이라면, B의 요청은 이미 도착했어도 읽는 일부터 기다려야 합니다.

## 1:35–3:20 · 무효화

> [무효화 표](../README_VER2.md#invalidation)에서 비교 코드의 삭제 요청과 현재 코드의 상품 수정을 짚는다.

다음은 무효화입니다. 같은 정보를 여러 번 찾을 때마다 원본을 읽는 대신, 한 번 읽은 결과를 잠시 저장해 둘 수 있습니다. 이게 캐시입니다. 그런데 원본을 고치고 나면 예전에 저장한 결과는 더 이상 맞지 않을 수 있습니다. 다음 사람이 그 예전 값을 받지 않도록 하는 게 무효화입니다.

비교 코드에서는 필요한 때에 특정 사용자의 캐시를 지워 달라고 요청합니다. 원하는 것만 골라 지울 수 있다는 게 장점입니다. 다만 언제 지울지는 요청하는 쪽이 챙겨야 합니다. 또 캐시를 지우는 동안 누군가 이미 원본을 읽고 있을 수 있습니다. 그 조회가 삭제보다 늦게 끝나면, 방금 지운 자리에 값이 다시 저장될 수 있습니다.

현재 코드에서는 상품을 고치면 캐시도 함께 처리합니다. 캐시에서 값을 찾을 때 쓰는 이름을 키라고 합니다. 상품을 고칠 때마다 키에 붙는 버전을 올리기 때문에, 다음 조회는 새 키로 값을 찾습니다. 예전 값을 지우는 데 실패해도 그 값이 다시 나오지 않는 이유입니다.

대신 기다림이 생깁니다. 누군가 같은 상품을 먼저 읽어서 캐시에 저장하는 중이라면, 수정 요청은 그 작업이 끝난 뒤에 처리합니다. 같은 상품을 읽고 고치는 일이 중간에 뒤섞이지 않게 상품마다 락을 두었기 때문입니다. 이 락은 API 프로그램 하나 안에서만 함께 씁니다.

## 3:20–4:00 · 선택 이유

> [선택 이유](../README_VER2.md#selection)에서 처리량 표의 ‘16개’ 행을 짚고, 바로 아래 팀의 판단으로 내려간다.

같은 컴퓨터에서 두 서버에 조회와 저장 명령을 보냈습니다. 연결 16개일 때 현재 코드는 초당 약 5만 건, 비교 코드는 약 14만 건을 처리했습니다. 이 조건에서는 비교 코드의 처리량이 약 2.8배였습니다. 두 코드는 언어와 구현도 달라서 스레드 방식만으로 이 차이를 설명하기는 어렵습니다.

저희가 더 중요하게 본 건 **상품을 고친 다음에 해야 할 일**이었습니다. 현재 코드는 같은 상품의 요청이 겹치면 잠시 기다릴 수 있습니다. 그래도 수정 요청 한 번이면 다음 조회부터 새 키를 씁니다. 상품을 고친 사람이 예전 캐시까지 따로 지울 필요가 없다는 점에서 현재 코드를 골랐습니다. 감사합니다.
