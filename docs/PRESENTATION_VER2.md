## 0:00–0:25 · 비교 기준과 순서

> README 첫 표에서 동시성과 무효화를 차례로 짚는다.

저희 조는 AI로 각각 Mini Redis를 만든 뒤 두 코드를 비교했습니다. 첫째는 **동시성**, 여러 요청이 겹칠 때 저장소를 어떻게 보호하는지입니다. 둘째는 **무효화**, 원본이 바뀌었을 때 예전 캐시를 어떻게 처리하는지입니다. 먼저 두 서버의 구조를 살펴보고, 각 방식을 쓰면 어떤 장점과 비용이 있는지 비교한 뒤, 마지막으로 왜 현재 코드를 선택했는지 설명드리겠습니다.

## 0:25–1:35 · 동시성

> [동시성](../README_VER2.md#concurrency)의 첫 표에서 구조와 대기 지점을 비교한 뒤, 아래 표의 2와 1을 짚는다.

먼저 동시성입니다. 서버에는 한 요청이 끝나기 전에 다른 요청이 들어올 수 있습니다. 두 요청이 같은 값을 바꾸려면 어느 쪽이 먼저 읽고 쓰는지 순서를 정해 줘야 합니다.

현재 코드는 연결마다 스레드를 하나씩 둡니다. 한 클라이언트가 다음 명령을 보내지 않아도 다른 스레드는 자기 요청을 처리할 수 있습니다. 저장소를 쓸 때는 공통 락을 잡습니다. 그래서 연결이 늘면 스레드도 늘고, 락을 오래 잡은 요청이 있으면 다른 키를 읽는 요청까지 기다립니다.

비교 코드는 한 스레드가 여러 연결을 살핍니다. 명령 하나를 끝내고 다음 명령으로 넘어가니 저장소를 잠글 필요가 없습니다. 그 대신 오래 걸리는 명령이 들어오면 그 뒤의 요청이 함께 밀립니다.

아래 표는 그 결과입니다. 처음 값이 0일 때 두 사람이 각각 증가 명령인 INCR를 보내면 두 코드 모두 결과는 2입니다. 반면 각자 GET으로 읽고 SET으로 저장하면, 둘 다 0을 읽은 다음 둘 다 1을 쓸 수 있습니다. 명령 하나는 보호돼도 두 명령 사이에는 다른 요청이 들어올 수 있습니다.

## 1:35–3:20 · 무효화

> [무효화](../README_VER2.md#invalidation)의 비교표를 보여준다. 이어서 조회 A와 삭제 B의 순서, 현재 코드의 가격 변경 예를 짚는다.

이제 무효화입니다. 캐시는 한 번 조회한 값을 저장해 뒀다가 다음 요청에 다시 쓰는 건데, 원본 가격이 바뀌면 예전에 저장한 가격은 더 이상 쓰면 안 됩니다. 두 코드의 차이는 누가 캐시를 지우고, 다음 조회가 어느 키를 읽는지에 있습니다.

비교 코드의 예제는 사용자 정보입니다. 호출자가 삭제를 요청하면 해당 사용자의 캐시 키를 지웁니다. 필요한 시점에 한 사람의 캐시만 지울 수 있다는 장점이 있습니다. 다만 이미 진행 중인 조회까지 멈추지는 않습니다.

표에서 A는 캐시가 비어 있어서 원본을 읽으러 갑니다. 그사이 B의 삭제 요청이 끝납니다. 뒤늦게 A가 원본을 받아 같은 키에 저장하면, 삭제가 끝난 뒤에 캐시가 다시 생깁니다. 각각의 명령이 순서대로 실행돼도 조회가 여러 단계라서 생길 수 있는 일입니다.

현재 코드는 상품 가격을 수정하는 API 안에서 캐시도 함께 처리합니다. 예를 들어 가격을 1,000원에서 1,200원으로 바꿀 때, 같은 상품을 먼저 조회하던 요청이 락을 잡고 있으면 캐시를 다 채울 때까지 수정이 기다립니다. 앞에서 본 저장소 락은 명령 하나를 보호했고, 이 상품별 락은 조회해서 캐시에 채우는 과정과 수정이 겹치지 않게 합니다.

수정할 차례가 되면 가격을 바꾸고, 버전을 올리고, 이전 키를 지웁니다. 삭제가 실패해서 버전 1에 1,000원이 남아 있어도 다음 조회는 버전 2를 찾아갑니다. 그래서 새 가격인 1,200원으로 캐시를 채웁니다.

## 3:20–4:00 · 현재 코드를 선택한 이유

> [선택 이유](../README_VER2.md#selection)의 마지막 표에서 감수한 비용과 선택한 동작을 왼쪽부터 짚는다.

두 코드 모두 동시에 들어온 증가 요청을 처리할 수 있었습니다. 저희가 선택 기준으로 삼은 건 가격을 바꾼 뒤의 첫 조회였습니다.

현재 코드에서는 같은 상품의 조회와 수정이 겹치면 한쪽이 기다려야 합니다. 또 상품별 락은 API 프로세스 하나 안에서만 공유됩니다. 그 비용은 있지만, 가격을 수정하는 사람은 캐시가 있는지 확인하거나 삭제 요청을 따로 보낼 필요가 없습니다. **상품 수정 한 번으로 다음 조회에 새 가격이 반영되는 점**을 중요하게 봐서 현재 코드를 선택했습니다. 감사합니다.
