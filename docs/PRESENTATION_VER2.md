## 0:00–0:20 · 발표 순서

> README의 발표 순서 표에서 동시성, 무효화, 팀의 결론을 차례로 짚는다.

저희 조는 AI로 만든 두 Mini Redis를 **동시성**과 **캐시 무효화**를 기준으로 비교했습니다. 두 기준을 차례로 살펴보고, 마지막에 각 코드에서 어떤 방식을 가져오기로 했는지 말씀드리겠습니다.

## 0:20–1:20 · 동시성

> [동시성 표](../README_VER2.md#concurrency)에서 코드 1과 코드 2의 ‘좋은 점’과 ‘감수할 점’을 짚는다.

먼저 동시성입니다. 두 코드 모두 저장소 작업은 하나씩 처리합니다. 여러 요청이 들어왔을 때 연결을 맡는 방식이 다릅니다.

코드 1은 **멀티 스레드 방식**입니다. 연결마다 스레드가 있어서 요청을 따로 받고, 응답이 늦으면 담당 스레드부터 살펴볼 수 있습니다. 대신 연결이 늘면 스레드도 늘고, 다른 스레드가 저장소 락을 잡고 있으면 기다립니다.

코드 2는 **단일 스레드 방식**입니다. 한 스레드가 준비된 요청을 골라 처리하므로 저장소 락을 두고 기다릴 일이 없습니다. 대신 긴 명령 하나가 끝날 때까지 뒤의 요청도 기다립니다.

## 1:20–2:45 · 무효화

> [무효화 표](../README_VER2.md#invalidation)에서 코드 2의 캐시 삭제 요청과 코드 1의 상품 수정을 짚는다.

다음은 **캐시 무효화**입니다. 조회 결과를 잠시 저장한 게 캐시고, 원본이 바뀐 뒤에 그 예전 값을 다시 쓰지 않게 하는 게 무효화입니다.

코드 2는 특정 사용자의 캐시를 따로 지울 수 있습니다. 삭제 시점은 요청하는 쪽이 정합니다. 먼저 시작한 조회가 늦게 끝나면, 지운 자리에 값을 다시 채울 수도 있습니다.

코드 1은 상품을 고칠 때 캐시를 찾는 이름인 **키**의 버전도 올립니다. 예전 캐시가 남아 있어도 수정이 끝난 뒤에는 새 키로 조회합니다. 또 같은 API 프로그램 안에서는 **상품별 락**을 써서 같은 상품의 조회와 수정을 차례로 처리합니다. 먼저 조회 중이면 수정은 그 조회가 끝날 때까지 기다립니다.

## 2:45–3:45 · 팀의 결론

> [팀의 결론](../README_VER2.md#selection)에서 ‘동시성’ 제목과 처리량 표의 ‘16개’ 행을 짚은 뒤, ‘캐시 무효화’로 내려간다.

동시성에서는 **코드 2의 단일 스레드 방식**을 선택했습니다. 연결마다 스레드를 둘 필요가 없기 때문입니다. 표에서 동시 연결 16개를 보면, 코드 2의 Redis 명령 처리량은 코드 1의 약 2.8배였습니다. 구현 언어와 명령 처리 코드의 차이도 포함된 결과입니다.

캐시 무효화에서는 **코드 1의 상품별 락과 버전 키**를 선택했습니다. 같은 상품의 조회와 수정이 순서를 지키고, 예전 캐시가 남아도 다음 조회에서 수정한 내용을 볼 수 있기 때문입니다. 다음 단계에서는 두 방식을 결합해 상품 API의 동작과 성능을 확인하겠습니다. 감사합니다.
