## 0:00–0:25 · 발표 순서

> README의 발표 순서 표에서 동시성, 무효화, 팀의 결론을 차례로 짚는다.

저희 조는 AI로 Mini Redis를 각각 만들고, 두 코드에서 어떤 방식을 가져올지 비교했습니다. 먼저 **동시성**, 여러 요청이 겹칠 때 Redis 서버가 어떻게 처리하는지 보겠습니다. 다음은 **캐시 무효화**, 원본이 바뀐 뒤 예전 값을 어떻게 처리하는지입니다. 마지막으로 두 기준에서 각각 어떤 방식을 선택했는지 말씀드리겠습니다.

## 0:25–1:35 · 동시성

> [동시성 표](../README_VER2.md#concurrency)에서 코드 1과 코드 2의 ‘좋은 점’과 ‘감수할 점’을 짚는다.

먼저 동시성입니다. 서버에서는 한 사람의 요청이 끝나기 전에 다른 사람의 요청이 들어올 수 있습니다. 두 코드 모두 저장소에서 값을 읽거나 바꾸는 일은 하나씩 처리합니다. 차이는 그동안 다음 요청을 누가 받아 주느냐에 있습니다.

코드 1은 **멀티 스레드 방식**입니다. 연결마다 담당 스레드가 있어서 A가 저장소를 쓰는 동안 B를 맡은 스레드는 B의 요청을 읽을 수 있습니다. B도 저장소를 쓰려면 A가 락을 놓을 때까지 기다립니다. 요청이 없는 연결에도 스레드 하나가 필요합니다.

B의 조회 응답이 늦다고 해보겠습니다. 이때는 B를 맡은 스레드부터 봅니다. 요청을 다 못 읽어서 기다리는 중이면 B와의 통신을 살펴봅니다. 이미 다 읽었는데 저장소 락에서 기다린다면, 어떤 작업이 락을 잡고 있는지 봅니다. 이렇게 어디부터 점검할지 좁힐 수 있습니다.

코드 2는 **단일 스레드 방식**입니다. 스레드 하나가 여러 연결을 살피다가 요청이 들어온 곳을 골라 처리합니다. 그래서 연결이 늘어도 담당 스레드를 더 만들 필요가 없습니다. 대신 그 스레드가 A의 긴 명령을 처리하는 중이라면, B의 요청은 이미 도착했어도 읽는 일부터 기다려야 합니다.

## 1:35–3:20 · 무효화

> [무효화 표](../README_VER2.md#invalidation)에서 코드 2의 캐시 삭제 요청과 코드 1의 상품 수정을 짚는다.

다음은 API에서 처리하는 캐시 무효화입니다. 같은 정보를 여러 번 찾을 때마다 원본을 읽는 대신, 한 번 읽은 결과를 잠시 저장해 둘 수 있습니다. 이게 캐시입니다. 그런데 원본을 고치고 나면 예전에 저장한 결과는 더 이상 맞지 않을 수 있습니다. 다음 사람이 그 예전 값을 받지 않도록 하는 게 무효화입니다.

코드 2에서는 필요한 때에 특정 사용자의 캐시를 지워 달라고 요청합니다. 원하는 복사본을 골라 지울 수 있고, 원본 사용자 정보는 그대로입니다. 언제 지울지는 요청하는 쪽이 챙겨야 합니다. 또 먼저 시작한 조회가 삭제보다 늦게 끝나면, 방금 지운 자리에 값이 다시 저장될 수 있습니다.

코드 1에서는 상품을 고치면 캐시도 함께 처리합니다. 캐시에서 값을 찾을 때 쓰는 이름을 키라고 합니다. 상품을 고칠 때마다 키에 붙는 버전을 올립니다. 그래서 예전 캐시를 지우지 못해도, 수정이 끝난 뒤 시작한 조회는 새 키로 수정한 내용을 찾습니다.

여기에는 **상품별 락**도 씁니다. 누군가 같은 상품을 먼저 읽어서 캐시에 저장하는 중이라면, 수정 요청은 그 작업이 끝날 때까지 기다립니다. 같은 API 프로세스에서 같은 상품을 읽고 고치는 일이 순서대로 진행되도록 하는 장치입니다.

## 3:20–4:00 · 팀의 결론

> [팀의 결론](../README_VER2.md#selection)의 ‘16개’ 행을 짚고, ‘팀의 판단’ 표를 위에서 아래로 따라간다.

동시 연결 16개에서 코드 2의 Redis 명령 처리량은 코드 1의 약 2.8배였습니다. 이 결과에는 스레드 방식뿐 아니라 구현 언어와 명령 처리 코드의 차이도 반영돼 있습니다.

Redis 서버에는 **코드 2의 단일 스레드 방식**을 쓰기로 했습니다. 한 스레드가 준비된 요청을 골라 처리해서, 연결마다 스레드를 둘 필요가 없기 때문입니다.

상품 API에는 **코드 1의 상품별 락과 버전 키**를 쓰기로 했습니다. 같은 상품의 조회와 수정은 순서를 지키고, 수정이 끝나면 다음 조회에서 새 키로 바뀐 내용을 읽을 수 있습니다. 다음 단계에서는 두 방식을 결합해 실제 상품 API의 동작과 성능을 확인하겠습니다. 감사합니다.
